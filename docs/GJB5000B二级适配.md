## 候选持久模型

先增加能复用的版本和稳定ID，再添加追踪/检查/度量，避免用JSON数组位置、名称字符串和当前状态替代长期证据。

| 模型 | 最少字段和约束 | 业务规则 |
|---|---|---|
| requirement | id、project_id、code、source_type/source_ref、current_revision_id、owner、状态、并发version | code项目内唯一；稳定ID不随编号/标题改变；来源可引用记录、附件或单位外部编号 |
| requirement_revision | requirement_id、revision_no、正文、验收准则、提出/确认信息、hash、创建人/时间；同需求revision_no唯一 | 已确认版本不可覆盖；补记业务时间与实际录入时间分开；删除/恢复不能重写已确认历史 |
| trace_link | project_id、source_type/id/revision、target_type/id/revision、relation、validity、change_id；同端点关系唯一 | 用独立关系表支持多对多；端点须存在且同项目；基线指向明确revision，当前对象变化则提示链接待复核，不静默换成新版本 |
| plan_revision / plan_item | project_id、document_revision_id、确认人/时间、基线task_id/日期/工时/达成准则、hash | 计划基线是快照；当前任务改期不覆盖历史；按期率说明使用哪份基线，未定计划/零分母不得冒充0或100% |
| config_item_revision | config_item_id、revision_no、标识/内容快照、文件blob或外部位置、sha256、状态、创建人/时间 | 外部路径只是引用，归档时需取得允许的实际内容或明确缺项；业务revision与行并发version分开 |
| baseline / baseline_item | project_id、名称、revision_no/状态、建立信息；成员config_item_id+revision_id+hash | 同一配置项可出现在多个基线且版本不同；建立后成员快照只读，新增变更产生新revision/基线 |
| change_request / change_impact | project_id、来源、原因、前后revision、影响对象/成本/日期、决定/依据、执行/验证链接 | 一个变更可影响多个需求、计划项或配置项；关联对象须同项目；决定和实施结果分离，不能仅用approved表示已完成 |
| quality_check_template_revision | 稳定template/item ID、revision、检查项/期望证据/适用条件、来源文件定位 | 不能在检查执行后改模板使历史结果变样；模板字段待单位核对，不内置编造条款 |
| quality_check_run / quality_check_result | 项目、template_revision、执行人/日期；item_id、问题/不适用结果、说明、证据、复核信息 | 执行时保存检查项快照；每个不符合须关联现有issue或明确处置依据；复核不把原发现改成从未发生 |
| metric_definition / metric_snapshot | 定义revision、单位、周期/阈值、公式/过滤口径；源范围/截止、分子/分母、缺数说明、值、生成时间、hash | 任意公式不执行用户代码；0/缺数据/不适用不同；已导出快照不可覆盖，重算生成新快照并标来源 |
| evidence_profile / evidence_link | 单位/项目配置revision、候选检查项、适用性/责任、核对状态、来源文件定位；entity/revision/hash | 待核对/已单位确认/不适用分开；不适用有理由；证据索引不复制原事实、不自动认定条款符合 |

现有document/document_revision、document_signature、entity_relation、export_job、time_entry继续复用。签署姓名是声明信息；没有可信身份和外部签名时不能称数字签名或证明不可伪造。审计链只能发现常规不一致，本机管理员仍可改库并重算整链。

## v0.2 P201～P207审查结论

| 计划项 | 本轮重点和容易遗漏的验收 |
|---|---|
| P201 | 移动须检查源/目标和祖先路径、同项目、版本及归档；排序/编码/汇总同事务。批量先验证全部对象，任何冲突回滚全部。重开是显式事件，不允许借普通PATCH修改终态。完整前后/内部拖放仍需UI证据 |
| P202 | 记录批量归类应拒绝归档项目、空/失效对象并写单项审计；标签/正文不丢失。完整图片灯箱的键盘/缩放/左右切换独立验收，不以“能显示图片”替代 |
| P203 | 草稿键至少隔离数据集/页面/实体版本；不得把同浏览器另一数据目录的草稿误套进来。保存成功才清草稿；失败/409可恢复；草稿附件不能来自另一数据集 |
| P204 | CLI迁移需要停止服务、源与目标路径关系检查、目标空目录或明确冲突、完整校验、保留原目录。健康页路径和操作步骤有助使用，但不等于完整目录/恢复图形向导 |
| P205 | 软删除对列表/搜索/今日/日志草稿/统计一致过滤；子树删除记录同一批次，恢复不能复活其他批次。恢复复查父项目/父任务是否活跃、归档/终态规则、唯一日志/编号冲突；首轮不物理清理图片 |
| P206 | 新完整包校验成功后才能清旧包；保护至少一个有效恢复点和恢复前回滚包。数量预算与字节预算的实际范围要写清；只显示磁盘空间不等于容量场景已验证 |
| P207 | 按实际排序验证分页去重/不漏；只有after_id不适合任意排序。中文短词/特殊字符召回、时区跨日/周/月回归与复合游标分别验收，未实现部分继续列待办 |
